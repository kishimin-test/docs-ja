# 管理者向け JWT 認証 API を実装する

| 項目 | 値 |
| ---- | -- |
| Issue | [#8](https://github.com/kishimin-ai-create/profile-hub/issues/8) |
| 英語タイトル | Implement JWT authentication for administrators |
| マイルストーン | v1 |
| ラベル | enhancement,area:api |

---

## 解決したい課題

管理画面のすべての機能は管理者だけが使えなければならないが、認証の仕組みがない。認証がないまま管理APIを実装すると、記事の作成・更新・削除が誰でも実行できる状態になる。

## 提案する解決策

JWT による管理者認証を実装する。

### エンドポイント

| メソッド | パス | 説明 |
| -------- | ---- | ---- |
| `POST` | `/api/admin/auth/login` | メールアドレスとパスワードで認証しトークンを発行 |
| `POST` | `/api/admin/auth/refresh` | トークンを再発行 |
| `POST` | `/api/admin/auth/logout` | セッションを終了 |
| `GET` | `/api/admin/auth/me` | ログイン中の管理者情報を返す |

### 要件

- パスワードは平文で保存せず、ソルト付きの実績あるパスワードハッシュ関数で保存する
- 管理API 配下は認証ミドルウェアで一括して保護し、エンドポイント単位の付け忘れが起きない構造にする
- 認証失敗時に、メールアドレスの存在有無を推測できる差 (メッセージ・応答時間) を出さない
- トークンの有効期限を設定し、期限切れトークンを拒否する
- ログアウト後に同じトークンを再利用できない
- トークンの保存方式を決定し、XSS・CSRF への対処と併せて記録する
- ログイン試行のレート制限を設ける
- パスワード、パスワードハッシュ、トークンをログとエラー応答に出力しない

### 決めること

- トークン保存方式 (HttpOnly + Secure + SameSite Cookie を第一候補とする)
- アクセストークンとリフレッシュトークンの有効期限
- 管理者アカウントの初期登録手段 (セルフサインアップは設けない)

## 代替案

- **セッションID + サーバー側セッションストア** — 失効を即座に反映できるが、ストア (Redis 等) の運用が増える。JWT を採用しつつ失効要件を満たす方式を検討する。
- **外部 IdP (OAuth/OIDC) に委譲する** — 実装は減るが、管理者 1 名の想定に対して依存が過大なため不採用。

## 受入条件

- [ ] 正しい認証情報でログインするとトークンが発行される
- [ ] 誤ったパスワードでログインが失敗し、応答からメールアドレスの存在有無を判別できない
- [ ] トークンなしで管理APIを呼ぶと 401 が返る
- [ ] 改ざんされたトークン、期限切れトークンで管理APIを呼ぶと 401 が返る
- [ ] ログアウト後に同じトークンで管理APIを呼ぶと 401 が返る
- [ ] パスワードが平文で保存されていない
- [ ] ログイン試行を連続して失敗させるとレート制限が働く
- [ ] ログ出力にパスワードとトークンが含まれない

## 対象外

- 管理画面側のログイン UI — 別Issue
- 多要素認証、パスワードリセットメール
- 管理者以外のロール

## 補足

- 依存: API 基盤の構築Issue
- セキュリティ要件は OWASP ASVS の認証・セッション管理の観点に沿って検証する
