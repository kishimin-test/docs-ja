# 記事 CRUD API を実装する (type: hobby/engineering, status: draft/published)

| 項目 | 値 |
| ---- | -- |
| Issue | [#9](https://github.com/kishimin-ai-create/profile-hub/issues/9) |
| 英語タイトル | Implement the article CRUD API (type: hobby/engineering, status: draft/published) |
| マイルストーン | v1 |
| ラベル | enhancement,area:api |

---

## 解決したい課題

趣味記事と技術記事を管理・公開する手段がない。記事は profile-hub の中心コンテンツであり、これがないと公開サイトも管理画面も成立しない。

また、下書き記事が公開サイトから閲覧できてしまう事故は、公開APIと管理APIで同じ記事取得処理を共有すると起きやすい。取得経路の段階で分離する必要がある。

## 提案する解決策

`Article` の CRUD API を、公開用と管理用に分けて実装する。

### 公開API (認証不要)

| メソッド | パス | 説明 |
| -------- | ---- | ---- |
| `GET` | `/api/public/articles` | 公開済み記事の一覧。`type` (hobby/engineering)、タグ、ページングで絞り込む |
| `GET` | `/api/public/articles/:slug` | 公開済み記事の詳細 |

### 管理API (認証必須)

| メソッド | パス | 説明 |
| -------- | ---- | ---- |
| `GET` | `/api/admin/articles` | 下書きを含む全記事の一覧 |
| `GET` | `/api/admin/articles/:id` | 記事の詳細 |
| `POST` | `/api/admin/articles` | 記事の作成 |
| `PUT` | `/api/admin/articles/:id` | 記事の更新 |
| `DELETE` | `/api/admin/articles/:id` | 記事の削除 |
| `PATCH` | `/api/admin/articles/:id/status` | 公開 / 下書きの切り替え |

### 要件

- 公開APIは `status = published` の記事のみを返す。下書きは一覧にも詳細にも現れない
- 存在しない記事と下書き記事で応答を変えず、下書きの存在を推測できないようにする
- 一覧は作成日時または公開日時の降順で、ページングを適用する
- `type` の値を増やしてもエンドポイントを追加せずに済む構造にする
- 入力検証 — タイトルの必須と長さ、本文の必須、スラッグの形式と一意性、`type` と `status` の値域
- 記事本文の想定形式 (Markdown / リッチテキスト) を決定し、公開側での描画時に HTML インジェクションが起きない扱いにする

## 代替案

- **単一エンドポイントで、認証状態に応じて下書きを含めるか切り替える** — 認証判定を 1 箇所でも誤ると下書きが公開される。公開/管理の分離を採用して不採用。
- **趣味用と技術用でエンドポイントを分ける** — `type` 追加のたびにエンドポイントが増える。不採用。

## 受入条件

- [ ] 認証なしで公開APIから公開済み記事の一覧と詳細を取得できる
- [ ] 下書き記事が公開APIの一覧に現れない
- [ ] 下書き記事のスラッグを直接指定しても公開APIから取得できず、存在しない記事と同じ応答になる
- [ ] `type` で趣味記事と技術記事を絞り込める
- [ ] 一覧がページングされ、指定件数を超えるデータを一度に返さない
- [ ] 認証済み管理者が記事を作成・更新・削除できる
- [ ] 認証なしで管理APIの記事作成を呼ぶと 401 が返り、記事が作成されない
- [ ] 公開/下書きを切り替えると、公開APIでの見え方が切り替わる
- [ ] タイトル未入力、不正な `type`、重複スラッグが 400 で拒否される

## 対象外

- 記事の全文検索
- 記事内の画像アップロード — v2
- カテゴリ・タグ自体の管理API (記事への付与のみ本Issueで扱う)

## デザインレビューによる更新 (2026-09-04)

記事本文は **Markdown** で執筆する。記事エディタのデザインが本文欄を `本文（Markdown）` (`#3:137`) とラベル付けしているため、Markdown かリッチテキストかという未決事項は解決した。

したがって、Markdown を HTML へ変換する経路で `script`、`on*` 属性などの実行可能な内容を通さないようにする必要がある。

受入条件に以下を追加する。

- [ ] 記事本文の Markdown から、描画結果に実行可能なスクリプトを注入できない
