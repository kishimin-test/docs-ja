## 解決したい課題

API アプリの土台がなく、認証・記事・プロフィールなどの個別エンドポイントを実装し始められない。土台なしに各エンドポイントを実装すると、エラー応答形式・バリデーション方法・ログ出力がエンドポイントごとにばらつく。

また、フロントエンド 2 アプリが API クライアントを型安全に生成するには、API 側が機械可読なスキーマ (OpenAPI) を出力している必要がある。

## 提案する解決策

`apps/api` に Hono ベースの API 基盤を構築する。

- ルーティング構成 — 公開API と 管理API をパス空間で分離する
- リクエスト検証 — スキーマ定義から検証し、検証エラーを一貫した形式で返す
- エラーハンドリング — アプリ内エラーを HTTP ステータスと応答ボディへ変換する共通ミドルウェア。本番環境では例外の詳細 (スタックトレース、SQL、内部メッセージ) を応答に含めない
- 構造化ログ — リクエストID、メソッド、パス、ステータス、処理時間。秘密情報とトークンをログに出さない
- CORS — 許可オリジンを public-web / admin-web に限定し、環境変数で設定する
- セキュリティヘッダーの付与
- ヘルスチェックエンドポイント (AppRun の死活監視用)
- OpenAPI スキーマの出力 — フロントエンドの API クライアント生成 (orval) の入力にする
- 設定の環境変数化 — DB接続、JWT秘密鍵、許可オリジン。既定値に本番用の値を埋め込まない
- レイヤ分離 — Route / Usecase / Repository の責務を分ける

## 代替案

- **公開APIと管理APIを同一パス空間に置き、エンドポイントごとに認証有無を分ける** — 認可漏れが起きたときに公開されてしまう。パスで分離しミドルウェアで一括して認証を要求する方式を採用して不採用。
- **OpenAPI を出力せず手書きの API クライアントを使う** — 2 アプリ分の型定義を手で維持することになり、API 変更時の追従漏れが起きる。不採用。

## 受入条件

- [ ] `bun run dev` で API が起動し、ヘルスチェックが 200 を返す
- [ ] 未定義のパスへのリクエストが一貫した形式の 404 応答を返す
- [ ] 不正なリクエストボディが 400 と、どのフィールドが不正かを示す応答を返す
- [ ] 想定外の例外発生時に 500 を返し、応答ボディにスタックトレースや内部メッセージが含まれない
- [ ] 許可していないオリジンからのブラウザリクエストが CORS で拒否される
- [ ] OpenAPI スキーマが出力でき、orval がそれを入力としてクライアントを生成できる
- [ ] DB接続情報と JWT 秘密鍵が環境変数から読み込まれ、コードにハードコードされていない

## 対象外

- 個別のエンドポイント実装 (認証・記事・プロフィール) — 別Issue
- 認証ミドルウェアの実装 — 別Issue
