# さくらのクラウド AppRun へのデプロイを構築する

| 項目 | 値 |
| ---- | -- |
| Issue | [#24](https://github.com/kishimin-ai-create/profile-hub/issues/24) |
| 英語タイトル | Deploy to Sakura Cloud AppRun |
| マイルストーン | v1 |

## 解決したい課題

3 つのアプリ (public-web / admin-web / api) と MySQL を稼働させる環境がなく、実装しても公開できない。既存の `render.yaml` は Render を前提としており、採用するさくらのクラウドと一致しない。

また、デプロイ手順が自動化されていないと、記事を公開するたびに手作業が発生し、prerender による静的 HTML の更新も滞る。

## 提案する解決策

さくらのクラウド AppRun (コンテナ) 上に 3 アプリをデプロイする。

### 構成

| 対象 | 稼働形態 |
| ---- | -------- |
| `apps/api` | AppRun 上のコンテナ |
| `apps/public-web` | ビルドした静的成果物の配信 (配信方式は本Issueで決定する) |
| `apps/admin-web` | ビルドした静的成果物の配信 |
| DB | さくらのクラウドの MySQL |

### 実装

- 各アプリの Dockerfile を Bun ベースで作成する。ビルド用と実行用のステージを分け、実行イメージに開発依存を含めない
- 環境変数と機密情報 (DB接続情報、JWT秘密鍵、許可オリジン) を AppRun の設定として管理し、リポジトリに含めない
- 独自ドメインの割り当てと TLS の設定
- 全通信を HTTPS にし、HTTP はリダイレクトする
- DB への接続元を必要な範囲に限定する
- API のヘルスチェックを死活監視に接続する
- DB マイグレーションの適用手順を決める (デプロイ時に自動適用するか、手動実行にするか)
- DB のバックアップと復旧手順を決める
- GitHub Actions からのデプロイを自動化し、認証情報を Secrets で管理する
- ステージング環境の要否を判断する
- 既存 `render.yaml` を削除または置き換える

## 代替案

- **さくらのクラウド サーバー (IaaS) 上に Docker と Nginx を自前構築する** — 自由度は高いが、OS 更新、TLS 更新、監視、バックアップの運用Issueが増える。AppRun を採用して不採用。
- **フロントエンドも AppRun のコンテナで配信する** — 構成は統一されるが、静的ファイル配信にコンテナを常時稼働させる必要がある。配信方式を本Issueで比較して決定する。

## 受入条件

- [ ] 3 アプリがさくらのクラウド上で稼働し、公開 URL からアクセスできる
- [ ] 公開サイトと管理画面が独自ドメインの HTTPS で配信される
- [ ] HTTP でアクセスすると HTTPS へリダイレクトされる
- [ ] API がヘルスチェックに応答し、異常時に検知できる
- [ ] DB接続情報と JWT 秘密鍵がリポジトリに含まれず、環境変数として設定されている
- [ ] DB へ想定外の接続元から接続できない
- [ ] main へのマージからデプロイまでが自動化されている
- [ ] マイグレーションの適用手順が文書化され、実行できる
- [ ] DB のバックアップが取得され、復旧手順が文書化されている
- [ ] 実行イメージに開発依存とソースマップが含まれていない
- [ ] `render.yaml` が削除または置き換えられている

## 対象外

- スケーリング設計、CDN の導入
- アクセス解析、APM の導入
