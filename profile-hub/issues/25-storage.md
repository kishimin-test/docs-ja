# さくらのオブジェクトストレージ (S3互換) との連携を実装する

| 項目 | 値 |
| ---- | -- |
| Issue | [#25](https://github.com/kishimin-ai-create/profile-hub/issues/25) |
| 英語タイトル | Integrate Sakura Object Storage (S3-compatible) |
| マイルストーン | v2 |
| ラベル | enhancement,area:infra |

---

## 解決したい課題

v1 では画像を URL 指定で扱うが、記事に画像を載せる、アバターを差し替えるといった運用には管理者がファイルをアップロードできる保存先が必要になる。保存先とアップロード経路がないと、メディア管理機能を実装できない。

アップロードは、経路を誤ると任意ファイルの設置や保存先の悪用につながるため、保存先の設計と検証を機能実装とは分けて確定させる。

## 提案する解決策

さくらのオブジェクトストレージ (S3互換) を画像の保存先として連携する。

### 実装

- バケットを作成し、公開読み取りの範囲を決める (公開画像のみ読み取り可能にし、一覧列挙を禁止する)
- API に画像アップロードのエンドポイントを追加する。管理API配下に置き、認証を必須にする
- アップロードの検証
  - 拡張子ではなく実際の内容から形式を判定し、許可する画像形式のみ受け付ける
  - ファイルサイズの上限を設ける
  - 保存時のファイル名を再生成し、アップロードされた名前をそのままパスに使わない
- `Media` テーブルへメタ情報 (元ファイル名、保存キー、形式、サイズ、代替テキスト) を保存する
- 削除時にストレージ上の実体も削除する
- 認証情報 (アクセスキー) を環境変数で管理する
- 公開画像の配信 URL を決める
- 開発環境での代替手段 (S3互換のローカルエミュレータなど) を用意する

## 代替案

- **画像を DB に保存する** — 構成は単純になるが、DB サイズと配信性能の面で不利。オブジェクトストレージを採用して不採用。
- **外部の画像ホスティングサービスに委ねる** — 実装は減るが、外部サービスへの依存とアカウント管理が増える。さくらのクラウドに構成を寄せる方針から不採用。
- **アプリのコンテナ内に保存する** — AppRun のコンテナは再作成されうるため、保存した画像が失われる。不採用。

## 受入条件

- [ ] 認証済み管理者が画像をアップロードでき、公開 URL から取得できる
- [ ] 認証なしでアップロードを呼ぶと 401 が返り、ファイルが保存されない
- [ ] 許可していない形式のファイルが、拡張子を画像に偽装しても拒否される
- [ ] 上限を超えるサイズのファイルが拒否される
- [ ] アップロードされたファイル名がそのまま保存キーに使われない
- [ ] バケットの一覧列挙が外部からできない
- [ ] メディアを削除するとストレージ上の実体も削除される
- [ ] アクセスキーがリポジトリに含まれず、環境変数から読み込まれる
- [ ] 開発環境で外部ストレージなしに動作確認できる

## 対象外

- メディア管理の画面 — 別Issue
- 画像のリサイズ、フォーマット変換、CDN 配信
