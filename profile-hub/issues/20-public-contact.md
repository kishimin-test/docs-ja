## 解決したい課題

サイトを見た人が連絡を取る手段がない。自己紹介サイトとして、問い合わせ経路がないと閲覧しても次の行動につながらない。

一方で、公開された問い合わせ経路は迷惑送信の標的になるため、連絡手段の提供方式を決めずに実装すると、スパム対策や個人情報の扱いが後付けになる。

## 提案する解決策

`/contact` に連絡手段を提供するページを実装する。

### 決めること

連絡手段の方式を先に決定する。

| 方式 | 内容 |
| ---- | ---- |
| A. リンク集のみ | SNSリンクとメールアドレスを表示する。実装が最小で、スパム対策も不要 |
| B. 問い合わせフォーム | 名前・メールアドレス・本文を送信する。API とスパム対策、送信内容の保存または転送が必要 |

### 方式 B を採用する場合の要件

- 入力検証 — 名前・本文の必須、メールアドレスの形式、本文の最大長
- サーバー側でも検証する。クライアント側の検証だけに依存しない
- スパム対策 (レート制限、ボット判定) を設ける
- 送信内容の扱い (DB 保存 / メール転送) と保持期間を決める
- 送信成功・失敗の結果を利用者に明示する
- 送信中は二重送信を防ぐ
- 個人情報の取り扱いを明示する

### 共通の要件

- SNSリンクを表示する
- キーボードのみで操作でき、エラーが支援技術に伝わる
- レスポンシブ対応

## 代替案

- **問い合わせを設けず SNS のみに誘導する** — 方式 A に相当する。実装とスパム対策のコストは最小だが、SNS を使わない相手からの連絡経路がない。方式選択時に判断する。
- **外部フォームサービスを埋め込む** — 実装は最小だが、外部スクリプトの読み込みが増え、CSP と個人情報の扱いが外部依存になる。

## 受入条件

- [ ] 連絡手段の方式 (A / B) が決定され、判断根拠が記録されている
- [ ] 未ログインで `/contact` を閲覧できる
- [ ] SNSリンクが表示され、正しい URL へ遷移する
- [ ] キーボードのみでページを操作できる
- [ ] モバイル幅で崩れずに表示される

### 方式 B を採用する場合に追加

- [ ] 必須項目を空で送信すると、API を呼ばずに検証エラーが表示される
- [ ] クライアント側の検証を回避して不正なリクエストを送っても、サーバー側で拒否される
- [ ] 連続送信するとレート制限が働く
- [ ] 送信成功と失敗が利用者に区別して表示される
- [ ] 送信ボタンを連打しても複数回送信されない

## 対象外

- 問い合わせ内容の管理画面での閲覧 (方式 B を採用し、必要になった場合に別Issueとする)

## デザインレビューによる更新 (2026-09-04)

### デザインが確定させた事項

デザイン (`Public / Contact — Desktop` `#2:188`) はページ上に直接こう書いている。

> v1 はフォームを持たず、SNS・メールへの導線に絞ったシンプルな構成です。 (`#2:202`)

**v1 はフォームを持たない。** GitHub / X / Email へのリンクのみを提供する。これにより「方式A / 方式B」の未決事項は解決し、フォームのバリデーション、スパム対策、送信内容の保存、個人情報の扱いは v1 のスコープから外れる。

### 内容

3 つのリンクカード。それぞれラベル、短い説明、遷移先を持つ。

| ラベル | 説明 | 遷移先 |
| ------ | ---- | ------ |
| GitHub | コード・個人開発を見る | `github.com` |
| X | 日々のこと・更新情報 | `x.com` |
| Email | 仕事やその他のご連絡 | メールクライアントを開く |

### 追加の要件

- SNSリンクは公開APIから取得し、再デプロイなしで管理者が変更できる
- メールリンクは平文のアドレスをそのまま露出させない。提示方法を決める

デザインレビューではこのページにレイアウトの破綻は見つからなかった。
