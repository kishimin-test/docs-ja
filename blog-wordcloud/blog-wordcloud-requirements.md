# Kotogumo 要件定義書

## 1. 概要

`Kotogumo` は、別サービスが定期収集しているメンバーのブログデータを利用し、メンバー単位で全ブログを形態素解析して WordCloud を生成・表示する Web アプリケーションである。

リポジトリ名は `blog-wordcloud` とする。

MVP では、利用者が

```text
グループ
  ↓
メンバー
  ↓
ワードクラウドを見る
```

の順に操作すると、選択したメンバーの保存済み全ブログを対象とした WordCloud を閲覧できる。

本アプリの目的は単純な頻出語の表示ではなく、ブログに現れる言葉遣い・口癖・絵文字などから「そのメンバーらしさ」を可視化することである。

ブログデータの収集・スクレイピングは本アプリの責務に含めない。

---

## 2. 目的

- メンバーごとのブログに現れる特徴的な言葉を視覚的に把握できるようにする
- 本人らしい言葉遣い・口癖・表現を WordCloud として可視化する
- メンバーごとの文章表現の違いを楽しめるようにする
- 形態素解析・WordCloud 生成機能をブログ収集サービスから独立させる
- 実際の解析結果を確認しながら、不要語を運用上調整できるようにする

---

## 3. MVP スコープ

### 3.1 基本フロー

1. グループを選択する
2. 選択したグループに所属するメンバー一覧を表示する
3. メンバーを選択する
4. 「ワードクラウドを見る」ボタンを押す
5. 選択したメンバーの全ブログを取得する
6. タイトル・本文を前処理する
7. 形態素解析および特徴表現の抽出を行う
8. ストップワードを除外する
9. 出現頻度を集計する
10. WordCloud を生成する
11. 生成結果を画面に表示する

### 3.2 集計単位

MVP では以下に固定する。

- 単位: メンバー
- 対象期間: DB に保存されている全期間
- 対象記事: 選択メンバーの保存済み全ブログ
- 記事単位解析: 対象外
- 期間指定: 対象外

### 3.3 管理機能

MVP では WordCloud 生成に加えて、ストップワード管理機能を提供する。

管理者はストップワード管理画面から、WordCloud に表示したくない一般語を追加・削除できる。

ストップワードは Kotogumo 全体で共通とする。

- WordCloud 表示
- ストップワード管理 UI
- 管理者ログイン UI

- 空状態表示
- エラー表示

### 4.2 Web API

- Hono
- TypeScript

責務:

- Python Analysis API の呼び出し
- Python との境界管理
- ストップワード CRUD

- WordCloud 生成リクエストの負荷制御
- HTTP エラーの整形

### 4.3 Analysis

- Python
- SudachiPy
- SudachiDict-core
- wordcloud
- Pillow

責務:

- 既存ブログ DB への接続
- グループデータ取得
- メンバーデータ取得
- ブログデータ取得
- 前処理
- 特殊表現抽出
- 形態素解析
- 原形正規化
- ストップワード除外
- 出現頻度集計
- WordCloud 生成
- 絵文字描画

既存ブログ DB に直接接続するアプリケーションコードは Python 側に限定する。

### 4.4 既存ブログ DB

別サービスが運用する MySQL を使用する。

既存ブログ DB には定期取得済みのブログデータが保存されている。

Kotogumo からは読み取り専用で利用する。

ブログの取得・更新・スクレイピングは別サービスの責務とする。

### 4.5 Kotogumo DB

Kotogumo 自身が管理するデータの保存には MySQL を使用する。

Hono が Kotogumo DB を所有し、MVP では以下を管理する。

- ストップワード
- 管理者認証に必要なデータ
- セッション管理に必要なデータ
- ログイン試行制限に必要な状態

Python は Kotogumo DB へ直接接続しない。

ブログ本文や加工済み本文を Kotogumo DB へ複製しない。

## 6. 解析要件

### 6.1 解析対象

選択したメンバーに紐づく、保存済みの全ブログを解析対象とする。

各ブログについて以下を使用する。

- タイトル
- 本文

タイトルと本文は同じ重みで扱う。

タイトルに含まれる表現を意図的に重く評価する処理は MVP では行わない。

### 6.2 解析方針

WordCloud は単純な日本語の単語頻度ではなく、ブログ文章から「そのメンバーらしさ」が伝わることを目的とする。

そのため、本人固有の文章表現を可能な限り保持する。

本人が繰り返し使用している表現についても、繰り返し自体をそのメンバーの特徴として扱い、出現頻度が高いことだけを理由に除外しない。

品詞分類や一般的な文章正規化よりも、本人らしい表現を失わないことを優先する。

### 6.3 前処理

形態素解析・出現頻度集計の前に、本人の文章表現ではないノイズを除去する。

以下は解析対象から除外する。

- URL
- HTML タグ
- 本文表示用マークアップ
- サイト由来の不要文字列
- サイト共通ナビゲーション
- サイト共通フッター
- サイト側のボタン文言
- 本文外の SNS 導線
- システム由来の定型文
- 装飾だけを目的とした罫線
- 装飾だけを目的とした連続記号
- その他、本人が記述した文章として意味を持たない文字列

URL は `http://` / `https://` などを解析前に除外する。

例えば以下のような装飾文字列は解析対象外とする。

- `━━━━━━━━━━━━━━━`
- `♡･･････♡`

ただし、本人が文章表現として使用している絵文字・顔文字・特徴的な記号表現は除外しない。

本人固有の挨拶・定型句・署名的表現についても除外しない。

### 6.4 抽出対象

MVP では、形態素解析によって以下の品詞を抽出する。

- 名詞
- 動詞
- 形容詞
- 副詞
- 感嘆詞

加えて、本人らしい文章表現として以下を保持する。

- 擬音語・擬態語
- 口癖
- 挨拶
- 特徴的な語尾
- 特徴的な言い回し
- 感嘆表現
- 絵文字
- 顔文字
- ハッシュタグ
- 本人が繰り返し使用する特徴的な表現

例えば以下のような表現を対象とする。

- `ゆっくり`
- `わー`
- `おお`
- `えっ`
- `うるうる`
- `ぽかぽか`
- `きゅんきゅん`
- `わくわく`
- `ドキドキ`
- `😊`
- `🥰`
- `✨`
- `💜`
- `☺️`
- `❤️`
- `🍵`
- `(❁´ω\`❁)`
- `*ˊᵕˋ*`

以下は原則として集計対象外とする。

- 助詞
- 助動詞
- 通常の記号
- 空白
- 改行

ただし、品詞だけを理由に本人らしい表現を失わないことを優先する。

形態素解析だけでは適切に抽出できない絵文字・顔文字・ハッシュタグ等については、専用の抽出処理と組み合わせる。

### 6.5 絵文字

絵文字は Unicode の grapheme cluster 単位で保持・集計する。

同じ絵文字が複数回使用されている場合、その回数を出現頻度へ反映する。

日本語・通常文字の WordCloud 描画には `Noto Sans CJK JP` を使用する。

絵文字描画用には、実行環境へ **Noto Color Emoji** を同梱し、OS のフォント環境へ依存しない。

通常の `wordcloud` によるレイアウト生成後、絵文字については Pillow による後段描画を行う。

絵文字描画時は以下を保証する。

- 絵文字の出現頻度を保持する
- 対応グリフが存在する絵文字を tofu（□）や空白として表示しない
- Variation Selector や ZWJ を含む絵文字を可能な限り grapheme cluster のまま扱う
- 描画不能な絵文字が存在しても解析処理全体を失敗させない
- 描画不能な絵文字はログへ記録する

絵文字が通常の日本語フォントで描画できないことを理由として解析対象から除外しない。

装飾文字列の一部としてのみ使用されている絵文字は、前処理による除外対象とする。

### 6.6 顔文字

顔文字は形態素解析へ渡す前に抽出する。

以下を組み合わせたルールベース方式を使用する。

- 正規表現
- Unicode 文字種
- 記号と文字の組み合わせ

抽出した顔文字は一時的にプレースホルダーへ置換し、形態素解析による分解を防止する。

解析終了後に元の顔文字へ復元し、頻度集計へ統合する。

顔文字を構成する各記号へ分解しない。

### 6.7 装飾文字列と顔文字の判別

ルールベースで判定する。

以下の特徴が強いものを装飾文字列として除外する。

- 同一記号または類似記号が長く連続する
- 罫線文字が主体である
- 文章を構成する文字をほぼ含まない
- 一定以上の長さを持つ装飾パターンである

短い記号表現や顔文字は一律に削除しない。

判別ルールは前処理モジュールへ集約し、テストケースによって管理する。

### 6.8 ハッシュタグ

ハッシュタグは `#` を含めた全体を一つの表現として保持する。

ハッシュタグ内部を形態素単位へ分割しない。

同じハッシュタグが複数の記事で使用されている場合も、その回数を出現頻度へ反映する。

URL 内のフラグメントなど、本人がタイトル・本文に記述したものではないハッシュタグは対象外とする。

### 6.9 擬音語・擬態語

SudachiPy の解析結果を基本とし、反復表現などをルールベース処理で補完する。

例:

- `わくわく`
- `きらきら`
- `ふわふわ`
- `ぽかぽか`
- `ドキドキ`

未知語であることだけを理由に除外しない。

### 6.10 原形への正規化

通常の文法的な活用については、出現頻度が複数の表記へ分散しないよう辞書形へ正規化する。

例:

- `食べた / 食べます / 食べて` → `食べる`
- `楽しかった / 楽しくて` → `楽しい`

ただし、本人が意図的に崩した表現や特徴的な表記については、本人らしさを失う可能性があるため機械的に通常表現へ変換しない。

例:

- `やったー`
- `わーーーい`
- `うれしーーい`

通常の文法的な活用と、意図的な表現崩しを同一視しない。

### 6.11 ストップワード

出現頻度が高くてもメンバーの特徴を表しにくい一般語については、ストップワードとして除外する。

初期ストップワードとして以下を登録する。

- `する`
- `ある`
- `いる`
- `こと`
- `これ`
- `それ`

ストップワードは品詞単位ではなく語単位で管理する。

本人固有の口癖・挨拶・特徴的な表現については、出現頻度が高いことだけを理由にストップワードへ追加しない。

ストップワードは管理画面から追加・削除できる。

追加・削除した内容は Kotogumo DB に永続化し、以降の WordCloud 生成へ反映する。

ストップワードは Kotogumo 全体で共通とする。

グループ別・メンバー別のストップワードは MVP では扱わない。

### 6.12 解析処理順序

1. 選択メンバーの全ブログを既存ブログ DB から取得する
2. タイトルと本文を取得する
3. URL・HTML・サイト由来ノイズを除外する
4. 装飾目的の記号列・罫線を除外する
5. ハッシュタグ・顔文字・絵文字など、形態素解析で失われる可能性がある表現を抽出・保持する
6. 残った日本語文章を SudachiPy で形態素解析する
7. 対象品詞を抽出する
8. 通常の活用語を辞書形へ正規化する
9. 擬音語・擬態語などの特徴的表現を保持する
10. 登録済みストップワードを除外する
11. 形態素解析結果と保持していた特殊表現を統合する
12. 各表現の出現頻度を集計する
13. WordCloud を生成する
14. 必要な絵文字を Pillow で描画する

## 7. WordCloud 要件

### 7.1 生成

Python の `wordcloud` を使用する。

出現頻度辞書から WordCloud を生成する。

画像処理には Pillow を使用する。

出現頻度が高い表現ほど視覚的に大きく表示する。

### 7.2 フォント

日本語・通常文字には `Noto Sans CJK JP` を使用する。

絵文字には `Noto Color Emoji` を使用する。

両フォントを実行環境へ同梱し、OS にインストールされているフォントへ依存しない。

WordCloud 本体と絵文字描画でフォントを使い分ける。

### 7.3 Sudachi

形態素解析には以下を使用する。

- SudachiPy
- SudachiDict-core

分割モードは `C` を初期値とする。

実データで複合語の分割に問題が確認された場合のみ分割モードを再評価する。

### 7.4 画像

生成形式は PNG とする。

Python Analysis API は生成した画像を `image/png` として Hono へ返却する。

Hono は `image/png` を React へ中継する。

MVP では生成画像を DB やファイルシステムへ永続保存しない。

### 7.5 表示

画面には以下を表示する。

- 選択したメンバー名
- WordCloud
- 生成中のローディング状態
- ブログが存在しない場合の空状態
- 解析・生成失敗時のエラー状態
- サーバー混雑時のエラー状態

### 7.6 ダウンロード

WordCloud の PNG ダウンロードは MVP 対象外とする。

## 8. 画面要件

MVP では以下の3画面を提供する。

### 8.1 WordCloud 画面

以下を表示する。

- プロダクト名 `Kotogumo`
- グループ選択
- メンバー選択
- 「ワードクラウドを見る」ボタン
- WordCloud 表示領域
- ローディング表示
- 空状態
- エラー表示

操作ルール:

- グループ変更時は選択済みメンバーをリセットする
- 生成中は同一画面からの生成ボタンを無効化する
- サーバー側でも生成処理の同時実行数を制限する

WordCloud の閲覧にログインは要求しない。

以下を提供する。

- 試行制限時のエラー表示
- ローディング表示

認証成功後はストップワード管理画面へ遷移する。

### 8.3 ストップワード管理画面

認証済み管理者のみアクセスできる。

以下を表示する。

- プロダクト名 `Kotogumo`
- 画面タイトル
- ストップワード追加フォーム
- 登録済みストップワード一覧
- 各ストップワードの削除操作
- WordCloud 画面へ戻る導線
- ログアウト操作
- ローディング表示
- 空状態
- エラー表示

以下の操作を提供する。

- 登録済みストップワードの一覧表示
- ストップワードの追加
- ストップワードの削除

MVP ではストップワードの編集機能を設けない。

変更する場合は対象を削除し、新しい語を追加する。

同一ストップワードの重複登録は許可しない。

空文字や空白のみのストップワードは登録できない。

## 9. API 要件

### 9.1 React → Hono

#### `GET /api/groups`

グループ一覧を取得する。

Hono は Python Analysis API の `GET /internal/groups` を呼び出して取得する。

#### `GET /api/groups/:groupId/members`

指定したグループに所属するメンバー一覧を取得する。

Hono は Python Analysis API の `GET /internal/groups/:groupId/members` を呼び出して取得する。

#### `POST /api/wordcloud`

WordCloud を生成する。

リクエスト例:

```json
{
  "memberId": "..."
}
```

Hono は Kotogumo DB からストップワードを取得し、Python Analysis API へ生成リクエストを送信する。

#### `GET /api/admin/stop-words`

認証済み管理者が登録済みストップワード一覧を取得する。

#### `POST /api/admin/stop-words`

認証済み管理者が新しいストップワードを登録する。

#### `DELETE /api/admin/stop-words/:id`

認証済み管理者が指定したストップワードを削除する。

#### `POST /api/admin/login`

メールアドレスとパスワードで管理者認証を行う。

認証成功時にサーバー側セッションを作成する。

#### `POST /api/admin/logout`

現在のセッションを無効化する。

### 9.2 Hono → Python Analysis API

#### `GET /internal/groups`

既存ブログ DB からグループ一覧を取得する。

成功レスポンス例:

```json
{
  "groups": [
    {
      "id": "...",
      "name": "..."
    }
  ]
}
```

#### `GET /internal/groups/:groupId/members`

既存ブログ DB から指定グループに所属するメンバー一覧を取得する。

成功レスポンス例:

```json
{
  "members": [
    {
      "id": "...",
      "groupId": "...",
      "name": "..."
    }
  ]
}
```

#### `POST /internal/wordcloud`

Hono は以下を送信する。

```json
{
  "memberId": "...",
  "stopWords": ["する", "ある", "いる"]
}
```

Python は `memberId` を使用して既存ブログ DB から対象データを取得する。

Python は Hono から受け取ったストップワードを使用する。

Python 自身は Kotogumo DB へ接続しない。

成功時は `image/png` を返却する。

### 9.3 エラー形式

JSON を返却する API のエラーは以下の形式へ統一する。

```json
{
  "error": {
    "code": "ERROR_CODE",
    "message": "..."
  }
}
```

最低限以下を定義する。

| HTTP | code                   | 用途                         |
| ---- | ---------------------- | ---------------------------- |
| 400  | `INVALID_REQUEST`      | 不正なリクエスト             |
| 401  | `UNAUTHORIZED`         | 未認証                       |
| 403  | `FORBIDDEN`            | CSRF / Origin 検証失敗等     |
| 404  | `NOT_FOUND`            | 対象データなし               |
| 409  | `DUPLICATE_STOP_WORD`  | ストップワード重複           |
| 429  | `RATE_LIMITED`         | ログイン試行制限             |
| 503  | `ANALYSIS_BUSY`        | 解析処理の受付上限超過       |
| 504  | `ANALYSIS_TIMEOUT`     | 解析タイムアウト             |
| 500  | `INTERNAL_ERROR`       | 想定外のエラー               |
| 502  | `ANALYSIS_UNAVAILABLE` | Python Analysis API 通信失敗 |

## 10. DB 要件

### 10.1 既存ブログ DB

MySQL を使用する。

Python のみ接続する。

Kotogumo からは読み取り専用で利用する。

最低限、以下に相当するデータを取得できることを前提とする。

```text
Group
- id
- name

Member
- id
- groupId
- name

Blog
- id
- memberId
- title
- body
- publishedAt
```

実際のテーブル名・カラム名は既存 DB のスキーマへマッピングする。

Kotogumo の都合による既存 DB のスキーマ変更は要求しない。

### 10.2 Kotogumo DB

MySQL を使用する。

Hono が接続する。

Python および React は直接接続しない。

### 10.3 StopWord

最低限以下を保持する。

```text
stop_words

id          BIGINT UNSIGNED AUTO_INCREMENT PRIMARY KEY
word        VARCHAR(255) NOT NULL UNIQUE
created_at  DATETIME NOT NULL
updated_at  DATETIME NOT NULL
```

日時は UTC で保存する。

削除は物理削除とする。

### 10.4 管理者

管理者は MVP では1ユーザーを前提とする。

最低限以下を保持する。

```text
admins

id             BIGINT UNSIGNED AUTO_INCREMENT PRIMARY KEY
email          VARCHAR(255) NOT NULL UNIQUE
password_hash  VARCHAR(255) NOT NULL
created_at     DATETIME NOT NULL
updated_at     DATETIME NOT NULL
```

パスワードそのものは保存しない。

### 10.5 セッション

認証状態はサーバー側セッションとして管理する。

セッション情報は Kotogumo 側で管理し、ブラウザには推測困難なセッション識別子のみを Cookie として保持する。

具体的なテーブル構造は利用するセッション実装に従う。

### 10.6 ログイン試行制限

ログイン試行制限はサーバー側で管理する。

MVP では最低限、以下を満たす。

- 同一送信元からの連続失敗を制限する
- 同一管理者アカウントに対する連続失敗を制限する
- 5回連続で認証に失敗した場合、15分間ログインを拒否する
- 制限中のログイン要求には HTTP `429` / `RATE_LIMITED` を返す
- 認証成功時は対象の連続失敗回数をリセットする
- クライアント側だけの制限に依存しない

IP アドレスのみを恒久的な利用者識別子として扱わない。

### 10.7 保存しないデータ

Kotogumo DB には以下を保存しない。

- ブログ本文
- 加工済みブログ本文
- 分かち書き済み本文
- 単語単位の解析結果
- WordCloud 画像
- 解析結果キャッシュ

## 11. 認証・セキュリティ要件

### 11.1 認証

管理者認証にはメールアドレスとパスワードを使用する。

パスワードハッシュには Argon2id を使用する。

認証状態はサーバー側セッションで管理する。

### 11.2 Cookie

セッション Cookie には以下を設定する。

- `HttpOnly`
- `Secure`
- `SameSite=Strict`
- `Path=/`

JavaScript からセッション識別子を取得できないようにする。

本番環境では HTTPS のみで送信する。

### 11.3 CSRF 防御

Cookie 認証を使用するため、状態変更を伴う管理 API は CSRF 防御を必須とする。

対象には最低限以下を含む。

- ストップワード追加
- ストップワード削除
- ログアウト

`POST` / `PUT` / `PATCH` / `DELETE` 等の unsafe method について、サーバー側でリクエスト元 Origin を検証する。

許可する Origin は設定された Kotogumo フロントエンドの同一 Origin のみに限定する。

`Origin` が存在し、許可 Origin と一致しないリクエストは HTTP `403` で拒否する。

Cookie の `SameSite=Strict` のみに依存せず、サーバー側でも Origin 検証を行う。

将来、フロントエンドと API を別 Origin に分離する場合は、Origin allowlist に加えて CSRF token 方式を導入する。

### 11.4 アクセス制御

WordCloud 閲覧機能は認証不要とする。

以下は認証済み管理者のみ実行できる。

- ストップワード一覧取得
- ストップワード追加
- ストップワード削除
- ログアウト

### 11.5 DB

既存ブログ DB の接続情報をブラウザへ露出しない。

DB 接続情報はサーバー側の環境変数等で管理する。

既存ブログ DB には読み取り専用ユーザーで接続する。

SQL はパラメータ化する。

### 11.6 Python Analysis API

Python Analysis API は内部サービスとして扱う。

インターネットから直接アクセス可能な公開 API としない。

可能な限りネットワークレベルで Hono からのみアクセス可能とする。

外部公開が必要な構成となる場合は、Hono と Python 間のサービス認証を必須とする。

## 12. 非機能要件

### 12.1 WordCloud 生成負荷制御

WordCloud 生成 API は認証不要で公開されるため、クライアント側のボタン無効化だけを負荷対策としない。

Hono または解析実行基盤で、サーバー側の同時実行数・待機キュー・タイムアウト・過負荷時の拒否を制御する。

MVP の初期値は以下とする。

- Python WordCloud 生成の最大同時実行数: `2`
- 待機キュー最大件数: `10`
- 解析タイムアウト: `60秒`
- キュー上限到達時: 新規生成要求を受け付けない
- 過負荷時レスポンス: HTTP `503`
- エラーコード: `ANALYSIS_BUSY`
- タイムアウト時レスポンス: HTTP `504`
- エラーコード: `ANALYSIS_TIMEOUT`

同時実行数とキュー件数は設定値として管理し、コード変更なしで調整可能とする。

キューに入った要求についてもタイムアウト対象とし、無制限に待機させない。

タイムアウト後も Python 側で不要な解析処理が無制限に継続しないよう、可能な限り処理をキャンセルまたは終了させる。

複数 Hono / Python インスタンスへ水平分割する場合、同時実行数が意図せずインスタンス数倍にならないよう実行基盤全体で上限を管理する。

### 12.2 UI

全ブログ解析中も UI を無反応にしない。

処理中であることを利用者へ表示する。

クライアント側でも生成中の重複操作を防止する。

ただし、クライアント側制御はサーバー側負荷制御の代替とはしない。

### 12.3 可用性

- Python の解析処理失敗によって Hono 自体を異常終了させない
- Python との通信失敗を適切に処理する
- タイムアウトを適切に処理する
- 過負荷状態を適切に処理する
- フロントエンドへ適切なエラーを返す
- ストップワード管理処理の失敗を成功として表示しない

### 12.4 保守性

以下をそれぞれ独立してテスト可能な構成とする。

- 既存ブログ DB からのグループ取得
- 既存ブログ DB からのメンバー取得
- 既存ブログ DB からのブログ取得
- 前処理
- 装飾文字列判定
- 絵文字抽出
- 絵文字描画
- 顔文字抽出
- ハッシュタグ抽出
- 擬音語・擬態語処理
- 形態素解析
- 原形正規化
- ストップワード処理
- 出現頻度集計
- WordCloud 生成
- ストップワード CRUD
- 管理者認証
- CSRF 防御
- ログイン試行制限
- WordCloud 同時実行制御

React / Hono / Python の責務を混在させない。

既存ブログ DB に依存するコードは Python 側へ閉じ込める。
