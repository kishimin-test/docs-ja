# mojica フロントエンドアーキテクチャ設計書

本書は[ui.md](./ui.md)・[component-design.md](./component-design.md)を実現するためのホスティング・レンダリング・BFF/API境界を定義する。API契約は[api.md](../api/api.md)に従う。

---

# 1. 要件・制約・前提

- **配信対象**: パブリック公開。認証なし、ユーザー情報の保存なし（ui.md §17 MVP対象外）。
- **SEO**: 不要。検索エンジンからの流入を想定しない画像生成ツール。
- **初期表示**: 特別な要件なし。バンドルサイズを小さく保つ程度の配慮でよい。
- **トラフィック変動**: MVPのため明示的な想定なし。CDNによる自動スケールを前提とする。
- **データ更新頻度**: 静的アセットのみ。動的データはユーザー操作起点の`POST /images`のみで、初期表示時のデータ取得はない。
- **可用性・コスト・運用体制**: 専任のサーバー運用チームを持たない前提とし、静的ホスティングで完結させる。
- **ホスティング**: バックエンド（ASP.NET Core、api.md）とは別のクラウド/CDN（Cloudflare Pagesなど）を想定。
- **API通信**: ブラウザからmojica APIへCORSで直接呼び出す。BFF/プロキシは設置しない。
- **ルーティング**: MVPは画像生成画面（`/`）と404 Not Found画面（ui.md §2, §19。Figmaデザイン`mojica / 404 Not Found`）の2ルート。存在しないパスへのアクセスをクライアント側で判定し、404画面を表示する必要があるためクライアントサイドルーターを導入する。
- **i18n**: 言語切替はURLではなく`Accept-Language`ヘッダーで表現する（ui.md §3, §13）。ロケール別のURLルーティングは不要。
- **セキュリティ**: フロントエンドは秘密情報を保持しない。認証情報・Cookie・セッションを扱わない。

---

# 2. 採用するホスティング・レンダリング・BFF・ルーティング構成

## レンダリング: CSR（Client-Side Rendering）

判断根拠：

1. パブリック配信だがSEO要件がないため、SSRを要求する条件に該当しない。
2. コンテンツの大半は静的だが、画面の主目的はフォーム送信という動的操作であり、SSG/ISRによる事前生成の恩恵が薄い。
3. 開発の単純さとホスティング運用負荷の低さを優先する。

結論として、SPA（CSR）として実装し、ビルド成果物を静的アセットとして配信する。

## ホスティング: CDN + 静的ホスティング（Cloudflare Pagesなど）

「CloudFront + S3」に相当する構成であり、以下を満たすことを確認して採用する。

- エッジ配信によるグローバルな低レイテンシ配信
- HTTPS既定、カスタムセキュリティヘッダー（`_headers`ファイル等）、SPAフォールバック、atomicデプロイ+即時ロールバックに対応
- サーバー運用が不要（コールドスタートやスケーリング設計が不要）

S3単体のWebサイトホスティングのようにHTTPS・カスタムヘッダー・Blue/Greenデプロイのいずれかが欠ける構成は本番アーキテクチャとして採用しない。

## BFF: なし。ブラウザからmojica APIへ直接CORS呼び出し

- フロントエンドは秘密情報（APIキー等）を扱わないため、BFFによる秘匿の必要性がない。
- バックエンド（api.md）のCORS設定でフロントエンドのオリジンを許可する。
- Cookie/認証情報を使わないため`credentials: "omit"`で送信し、Cookieベースのセッションを前提としたCSRF対策は不要とする。

## ルーティング

- クライアントサイドルーター（TanStack Router、file-based routing）を導入する。`src/routes/`配下のファイル（`__root.tsx`・`index.tsx`）からVite plugin（`@tanstack/router-plugin/vite`）が`src/routeTree.gen.ts`を自動生成する（手動編集禁止）。ルート定義は`/`（画像生成画面、`index.tsx`）と、ルートに属さない未マッチパス全般を扱う`notFoundComponent`（404 Not Found画面、`__root.tsx`）の2つ（component-design.md参照）。
- ホスティング側のSPAフォールバック設定（存在しないパスを`index.html`へフォールバックする設定）を有効にする。ホスティングは常に`index.html`を返し、実際の404判定・表示はTanStack Routerの`notFoundComponent`がクライアント側で行う。
- ロケールはURLに含めず、クライアント状態（`localStorage`のキー`"locale"`、値は`"ja"`または`"en"`）で保持し、`Accept-Language`ヘッダーとしてAPI呼び出し時に付与する。

## 環境設定（APIエンドポイントの解決）

- SSRのような実行時のサーバー環境変数解決ができないため、mojica APIのベースURLはビルド時の環境変数（例: Viteの`import.meta.env.VITE_API_BASE_URL`）として注入する。
- 環境（本番/プレビュー等）ごとに異なるAPIベースURLでビルドし、ホスティングプラットフォームのデプロイ設定に対応付ける。
- 複数環境間で同一ビルド成果物を昇格させる運用が必要になった場合は、実行時に`config.json`を取得する方式への切り替えを検討する（MVPでは過剰設計のため採用しない）。

# 3. 採用理由と採用しなかった代替案

| 代替案                                                                | 採否               | 理由                                                                                                                                                                                                                                                                             |
| --------------------------------------------------------------------- | ------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| SSR（Node server / FaaS）                                             | 不採用             | SEO・最速初期表示の要件がない。サーバー運用またはFaaSの複雑さに見合う価値がない                                                                                                                                                                                                  |
| SSG/ISR                                                               | 不採用             | 画面の主目的はフォーム送信という動的操作であり、静的コンテンツの事前生成による恩恵が薄い                                                                                                                                                                                         |
| Hybrid                                                                | 不採用             | 画像生成画面・404画面ともにSEO要件がなく、全ルートがCSRで完結する。レンダリング方式を混在させる理由がない                                                                                                                                                                        |
| BFF（Route Handler等のプロキシ）                                      | 不採用             | 秘密情報や内部オリジンを扱わないため、プロキシによる秘匿・ヘッダー制御の必要性が薄い。CORS直接呼び出しの方が構成が単純                                                                                                                                                           |
| バックエンドと同一クラウドでのホスティング                            | 不採用             | 別のCDN/静的ホスティングを採用する方針を確認済み。配信対象がCSRの静的アセットのみのため、バックエンドのクラウドに縛られる理由がない                                                                                                                                              |
| ルーティング: TanStack Router（file-based routing）                   | 採用               | Figmaデザインに404 Not Found画面が存在し、存在しないパスの判定をクライアント側で行う必要がある。`gen/api/`をOrvalで生成しTanStack Queryを使う構成とツールファミリーを揃えられ、型安全なルート定義（パラメータ・検索パラメータの型推論）が既存のZod/OpenAPI型駆動の方針と一貫する |
| ルーティング: React Router（`createBrowserRouter`）                   | 不採用             | CSRのSPAで採用実績は多いが、TanStack Queryと組み合わせた際の型推論の一貫性がTanStack Routerほど高くない。ルート定義とデータ取得の型が別エコシステムになる                                                                                                                        |
| ルーティング: 単一ルート運用のまま404はUIで代替表示（ルーター未導入） | 不採用             | 存在しないパスにアクセスした場合もURLは変わらず`/`の画像生成画面が表示され続け、Figmaの404画面の意図（誤ったURLであることをユーザーに伝える）を実現できない                                                                                                                      |

# 4. セキュリティ・キャッシュ・性能・運用上のリスク

## セキュリティ

- **CORS**: mojica API側で許可オリジンをフロントエンドの本番/プレビュードメインに限定する。プレビューデプロイは動的なサブドメインを発行するホスティングが多く、許可オリジンのパターン管理（プレビュー環境用の許可方法）をバックエンド側と合意する必要がある（残存リスク）。
- Cookie/認証情報を使わないためCSRF対策は不要だが、`Content-Type: application/json`のみを許可し、単純CORSリクエストの誤用を防ぐ。
- セキュリティヘッダー（CSP、X-Content-Type-Options、Referrer-Policy、Permissions-Policy）をホスティング側の設定で付与する。CSPの`connect-src`にmojica APIのオリジンを含める。
- ブラウザに秘密情報・内部オリジンを渡さない（APIベースURLは公開情報として扱う）。

## キャッシュ

- 静的アセット（JS/CSS、ハッシュ付きファイル名）は長期キャッシュ（immutable相当）とする。
- `index.html`は更新をすぐ反映できるよう`no-cache`または短いTTLとする。
- `POST /images`はキャッシュ対象外（ブラウザは元々POSTをキャッシュしない）。生成画像はサーバーに保存しない（api.md §10）ためCDNキャッシュの対象にもならない。

## 性能

- CSRのため初期表示（JS実行完了まで）はSSRより遅くなる。フォーム1画面のみのため追加のコード分割は不要と判断するが、バンドルサイズは計測して確認する。
- CDNのエッジ配信により静的アセットのTTFBは各地域で高速化される。

## 運用

- サーバープロセスが存在しないため、コールドスタートやスケーリング設計が不要。
- デプロイはCDNプラットフォームのatomicデプロイ機能で行い、問題発生時は直前のデプロイへ即時ロールバックする。
- バックエンドとフロントエンドが別クラウドのため、CORS設定変更時は両チーム間の調整が必要になる。

# 5. 検証項目・デプロイ/ロールバック計画・残存リスク

## 検証項目

- 本番相当のビルドで、mojica APIへの`POST /images`がCORSエラーなく成功すること（preflightの`OPTIONS`が`Content-Type`・`Accept-Language`を許可していること）
- ホスティング側の設定によるセキュリティヘッダーが実際のレスポンスに付与されていること
- 直接`index.html`以外のパス（例: `/foo`）へアクセスした場合に、ホスティングのSPAフォールバックで`index.html`が返り、TanStack Routerの`notFoundComponent`により404 Not Found画面が表示されること
- 代表的な端末・回線での初期表示速度（LCP等）
- 言語切替後、`Accept-Language`ヘッダーが正しく送信され、表示文言とAPIエラーメッセージの言語が一致すること
- APIエラー（400/429/500/502/504）発生時に、フィールドに紐づかないエラーとして表示できること（component-design.md のOrval生成ミューテーションフックの`isError`/`error`と整合）

## デプロイ/ロールバック計画

- CIでビルドした静的アセットをCDNプラットフォームへデプロイする。
- デプロイはatomicに切り替わり、問題発生時は直前のデプロイへ即時ロールバックする（サーバー再起動やインスタンス入れ替えは不要）。
- 本番反映前にプレビューデプロイでmojica API（またはステージング相当のAPI）との疎通を確認する。

## 残存リスク

- プレビューデプロイのオリジンに対するCORS許可方法がバックエンド側で未確定。
- 複数環境（本番/ステージング/プレビュー）を運用する場合、ビルド時環境変数によるAPIベースURL注入では同一成果物を環境間で昇格できない。運用が複雑化した場合は実行時`config.json`方式への移行を検討する。
- ホスティングプラットフォームの具体的な製品選定・契約は未確定。
